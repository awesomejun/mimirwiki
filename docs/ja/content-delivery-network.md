# コンテンツデリバリーネットワーク

> コンテンツデリバリーネットワーク（CDN）は、ウェブコンテンツの複製をエンドユーザーに近い拠点に保存する分散サーバー群である。クライアントとオリジンサーバーの間でマネージド共有HTTPキャッシュとして機能し、遅延を低減し、オリジンサーバーの負荷を抑え、可用性を高める。関連するIETFの文書は、HTTPキャッシング、対象指定キャッシュヘッダー、エニーキャストサービス分散、およびCDN相互接続を扱っている。

コンテンツデリバリーネットワーク（Content Delivery Network、CDN）は、ウェブオブジェクトの複製を保存し、エンドユーザーに近い拠点からクライアントのリクエストを処理する地理的に分散したサーバーシステムである。クライアントとオリジンサーバーの間でマネージド共有HTTPキャッシュとして動作することで、応答遅延を短縮し、オリジンサーバーの負荷を軽減し、高トラフィック下での配信の信頼性を高める。関連するインターネット技術タスクフォース（IETF）の文書は、HTTPキャッシング（RFC 9111）、対象指定CDNキャッシュ制御（RFC 9213）、エニーキャストサービス分散（RFC 4786）、およびCDN相互接続（RFC 6707およびRFC 7336）を扱っている。商用CDNは世界各地のPoP（Point of Presence）を通じて静的アセットと動的ウェブコンテンツの両方を配信する一方で、キャッシュの鮮度維持、セキュリティ露出、サードパーティの可用性への依存といった運用上のトレードオフを伴う。

**別名:** CDN, Content Delivery Network, Content Distribution Network, コンテンツ配信ネットワーク, コンテンツデリバリーネットワーク（CDN）

## コンテンツデリバリーネットワークのアーキテクチャとPoP

コンテンツデリバリーネットワーク（CDN）は、ウェブデータの複製を保存し、エンドユーザーに近い拠点からクライアントのリクエストを処理する地理的に分散したキャッシュサーバー群として動作する。[6][8] オリジンサーバーはHTMLページ、スタイルシート（CSS）、JavaScriptファイル、画像、メディアファイルといったウェブオブジェクトの原本を保持し、ウェブサーバー、カスタムHTTPサーバー、またはAmazon S3バケットなどのオブジェクトストレージサービスがその役割を担う。[6][8] エッジロケーション（PoP：Point of Presenceとも呼ばれる）は、視聴者の近くにオブジェクトの複製をキャッシュするためにCDNが各地のデータセンターに配置したサーバーの集合である。[8]

クライアントがCDN経由で提供されるオブジェクトをリクエストすると、ネットワークは低遅延で応答できるエッジロケーションへリクエストをルーティングする。[8] 利用可能な複製がそのエッジロケーションに既に保存されている場合、サーバーはオリジンサーバーへリクエストを転送せずに直接返す。[7][8] オブジェクトが存在しない場合、エッジサーバーはオリジンサーバーから原本を取得し、後続のリクエストに備えて複製をキャッシュする。[8] 地理的距離は遅延に比例して影響するため、エンドユーザーの近くにサーバーを配置することで往復配信時間が短縮される。[6] Amazon CloudFrontなどの商用プロバイダーは、独自のプライベートバックボーンネットワーク（AWSバックボーンネットワーク）経由でリクエストをルーティングして経由する中間ネットワークの数を減らし、最初の1バイトを受信するまでの時間（Time to First Byte）を短縮してデータ転送速度を高めるとともに、可用性確保のために複数のエッジロケーションに複製を保持している。[8]

HTTPアーキテクチャにおいて、CDNはサービス運用者が明示的に配備するマネージド共有キャッシュとして機能し、リクエスト解析、Cookieベースのセッション復元、データベースクエリ、テンプレートレンダリングといった処理をオリジンサーバーからオフロードする。[7] RFC 6707は、キャッシュ可能なコンテンツに対するCDN導入の主な利点として、配信コストの削減、エンドユーザーの体感品質（QoE）の向上、配信の堅牢性向上の3点を挙げている。[3] CDNは静的ライブラリ（BootstrapやjQueryなど）、完全な静的ウェブサイト、および動的ウェブコンテンツの配信に広く利用されている。[6][8] 2026-11-23時点で、Amazon CloudFrontはディストリビューション設定（オリジンサーバー、ロギング、割り当て済みまたはカスタムのドメイン名、プライベートコンテンツ向けの署名付きURLや署名付きCookieなどのアクセス制御）を全エッジロケーションへ伝播する一方、オブジェクト自体はオンデマンドで取得しており、単独のスタンダードディストリビューションとCloudFront SaaS Managerによるマルチテナントディストリビューションの双方を提供している。[8] 2026-11-23時点で、CloudFrontはエッジロケーションでオブジェクトをデフォルト24時間キャッシュし（最小0秒、固定の上限なし）、エッジロケーションからのアウトバウンドデータ転送およびHTTP/HTTPSリクエストに対して課金する一方、AWSオリジン（Amazon S3、Elastic Load Balancing、Amazon API Gateway）からCloudFrontへの転送には料金を課していない。[8]

## コンテンツデリバリーネットワークにおけるHTTPキャッシングの仕組み（RFC 9111）

コンテンツデリバリーネットワークのキャッシングは、インターネット技術タスクフォース（IETF）が2022年6月にRFC 9111（STD 98）として発行したHTTP Caching仕様に基づいている。この仕様はR. Fielding（Adobe）、M. Nottingham（Fastly）、J. Reschke（greenbytes）によって編集され、RFC 7234を廃止している。[1] RFC 9111はHTTPキャッシュを、レスポンスメッセージのローカルストアおよびその保存・取得・削除を制御するサブシステムと定義しており、同等の後続リクエストに対する応答時間とネットワーク帯域消費を削減する。[1]

HTTPキャッシングでは、キャッシュを単一ユーザーに奉仕するプライベートキャッシュ（通常はウェブブラウザ内に存在）と、クライアントとサーバーの間の中間ノードに配置されて複数ユーザーに奉仕する共有キャッシュ（shared cache）に分類する。[1][7] MDN Web Docsは共有キャッシュをさらに、通常はサービス開発者の管理外で運用されるプロキシキャッシュ（proxy cache）と、リバースプロキシ、CDN、Cache APIを使用するサービスワーカーなど、サービス運用者が明示的に配備するマネージドキャッシュ（managed cache）に細分化している。[7] HTTPS暗号化の普及に伴い、経路上のネットワークプロキシキャッシュは一般に暗号化トラフィックを検査やキャッシュを行わずそのままトンネリングするが、組織が管理する認証局（CA）を用いてTLSブリッジングプロキシがトラフィックを復号する管理された企業環境は例外となる。[7]

キャッシュは少なくともリクエストメソッドとターゲットURIで構成されるキャッシュキーを用いて保存済みレスポンスを識別するが、実際に運用されている多くのキャッシュはURIをキーとして`GET`レスポンスのみを保存している。[1] コンテンツネゴシエーションが行われるリソースでは、キャッシュは`Vary`レスポンスヘッダーで指定されたリクエストヘッダーをキャッシュキーに組み込む。[1] キャッシュされる項目の大半は`GET`リクエストに対する`200 (OK)`レスポンスであるが、規則で許可される場合にはリダイレクト、`404 (Not Found)`レスポンス、`206 (Partial Content)`レスポンスも保存できる。[1] RFC 9111のセクション3では、共有キャッシュは`no-store`が含まれる場合、変更された共有保存を許可しない`private`が含まれる場合、または共有キャッシングを明示的に許可するレスポンスディレクティブなしにリクエストへ`Authorization`ヘッダーが含まれる場合には、レスポンスの保存を避けなければならない。さらに保存には、理解可能なメソッド、最終ステータスコード、および`public`、`Expires`、`max-age`、`s-maxage`、キャッシュ拡張、またはヒューリスティックにキャッシュ可能なステータスコードといったキャッシング指標が必要となる。[1]

保存されたレスポンスは、フレッシュ（fresh：オリジンへ問い合わせずに再利用可能）またはステイル（stale：切断状態のキャッシュにステイル配信が許可されていない限り、鮮度回復のためオリジンへの再検証が必要）のいずれかの状態にある。[1][7] 鮮度計算には整数オーバーフローを防ぐため`2147483648`（2^31、68年以上）を上限とする非負の`delta-seconds`値が用いられる。[1] 共有キャッシュは保存経過時間を`Age`ヘッダーで通知する。例えば、`Cache-Control: max-age=604800`（1週間）を持つレスポンスを共有キャッシュが1日間保存した場合は`Age: 86400`を付与して配信し、下流クライアントには残り518,400秒の鮮度が残る。[7] `Cache-Control`が省略された場合、ヒューリスティックキャッシングによって`Last-Modified`ヘッダーを持つレスポンスを最終更新からの経過時間のおよそ10%の期間再利用することがある。[7] 基本のHTTPキャッシング仕様は明示的な削除メカニズムを定義していないため、CDNなどのマネージドキャッシュはダッシュボード、API呼び出し、または再起動による帯域外パージを提供し、Varnish Configuration Language（VCL）ルールのようなカスタムキャッシュロジックを実行できる。[7]

| ヘッダーまたはディレクティブ | 適用範囲 | HTTPおよびCDNキャッシングにおける役割 |
| --- | --- | --- |
| `Cache-Control: max-age` | プライベートおよび共有キャッシュ | レスポンス生成時点からの鮮度保持期間を秒単位で指定する。[1][7] |
| `Cache-Control: s-maxage` | 共有キャッシュ | 共有キャッシュ専用の鮮度保持期間を指定する。[1][2] |
| `Cache-Control: private` | プライベートキャッシュ | パーソナライズされたレスポンスの保存を単一ユーザーキャッシュに制限する。[1][7] |
| `Cache-Control: no-store` | すべての標準キャッシュ | キャッシュによるレスポンスの保存を禁止する。[1] |
| `Cache-Control: no-cache` | すべての標準キャッシュ | 保存済みレスポンスを再利用する前にオリジンへの検証を要求する。[1][2] |
| `Age` | 共有キャッシュ | レスポンス生成からの経過秒数を通知する。[1][7] |
| `Expires` | レガシーHTTP/1.0およびHTTP/1.1 | キャッシュの有効期限を明示的なタイムスタンプで指定する。[1][7] |
| `Vary` | キャッシュキー構成 | コンテンツネゴシエーションのためキャッシュキーに組み込むリクエストヘッダーを列挙する。[1] |

## 対象指定HTTPキャッシュ制御とCDN-Cache-Control（RFC 9213）

コンテンツデリバリーネットワークの配備環境は、オリジンサーバーキャッシュ、オリジンネットワークキャッシュ、およびブラウザキャッシュと並ぶ多層キャッシュトポロジーの中に配置されることが多く、キャッシュの種類ごとに異なるキャッシュポリシーを指示する手段が求められる。[2] `Cache-Control`には共有キャッシュ向けの`s-maxage`が含まれるものの、`stale-while-revalidate`のような他のディレクティブにわたる一貫した対象指定手段を欠いている。[2] 初期のCDN実装は`Surrogate-Control`などのベンダー固有ヘッダーに依存しており、プロバイダー間の相互運用性が低かった。[2][7]

2022年6月、IETFはAkamaiのS. Ludin、FastlyのM. Nottingham、および[Cloudflare](https://mimirwiki.com/ja/wiki/cloudflare)のY. WuによるStandards Track仕様RFC 9213（Targeted HTTP Cache Control）を発行した。[2] RFC 9213は対象指定キャッシュ制御（Targeted Cache-Control）HTTPレスポンスヘッダーの一般的な規約を確立し、CDNキャッシュ専用の`CDN-Cache-Control`を定義している。[2] CDNとの間でキャッシュ無効化の仕組みを持つパブリッシャーは、`CDN-Cache-Control`に長い有効期間を設定しつつ、ブラウザやその他の中間キャッシュ向けには`Cache-Control`で短い有効期間を維持できる。[2]

対象指定キャッシュ制御ヘッダーはHTTP Dictionary Structured Fieldsとして定義され、各辞書メンバーがHTTPキャッシュレスポンスディレクティブ（拡張ディレクティブを含む）に対応し、その値はStructured FieldsのBoolean、String、Token、Integer、またはDecimal型にマッピングされる。[2] エラー処理が`Cache-Control`と異なるため、実装は対象指定フィールドに対してStructured Fieldsパーサーを使用し、空であるか構文解析エラーを生じるフィールドを無視して他のキャッシュ制御メカニズムへフォールバックする。[2]

RFC 9213を実装する各キャッシュは、`[ExampleCDN-Cache-Control, CDN-Cache-Control]`のように優先度の高い順から低い順へ並べたヘッダー名のターゲットリストを保持する。[2] キャッシュは受信した各レスポンスに対し、ターゲットリスト上で最初に見つかった有効かつ空でないフィールドを選択してキャッシング挙動を制御し、そのレスポンス上の`Cache-Control`と`Expires`を無視する。[2] キャッシュのターゲットリストに含まれない対象指定フィールドは、そのキャッシュの挙動を変更することなくそのまま通過させなければならない。[2] 対応するキャッシュは対象指定フィールド内で`max-age`、`must-revalidate`、`no-store`、`no-cache`、`private`の5つのディレクティブを実装する必要がある。[2] 優先順位は`Cache-Control`と一致しており、`no-store`と`no-cache`は`max-age`を無効化し、認識されない拡張ディレクティブは無視される。[2]

## エニーキャストサービス分散（RFC 4786）

エニーキャストルーティングは、1つのサービスアドレスを2つ以上の独立したノードで到達可能にし、ルーティングシステムがクライアントリクエストをそのいずれかのノードへ届ける方式である。これはJ. Abley（Afilias Canada）とK. Lindqvist（Netnod Internet Exchange）によるIETFのBest Current PracticeであるRFC 4786（BCP 126、2006年12月）に文書化されている。[5] RFC 4786はインターネットサービス全般を対象としており、主な例としてDNSサーバーを挙げている。[5] エニーキャストを配備するには、運用者が安定したサービスアドレス（IPv4またはIPv6）を2つ以上の独立したエニーキャストノードに割り当て、ルーティングシステム内でそのアドレスへの到達可能性を広報する。[5]

クライアントがエニーキャストのサービスアドレスへパケットを送信すると、ルーティングシステムはネットワークトポロジーとリクエストの発信元に基づいて、利用可能なノードのいずれかへデータグラムを転送する。[5] 特定のノードへパケットが到達するネットワークのトポロジー的領域はキャッチメント（catchment）と呼ばれる。[5] RFC 4786は2つの配備スコープを区別している。内部ゲートウェイプロトコル（IGP）を通じて経路を伝播しルーティングシステムの一部からのみノードを可視化するローカルスコープ・エニーキャストと、境界ゲートウェイプロトコル（BGP、RFC 4271）を用いてグローバルインターネット全体に到達可能性を広報するグローバルスコープ・エニーキャストである。[5] エニーキャストはサーバーリファラルやラウンドロビンDNSを必要とせずに機能するが、アプリケーションは必要に応じて名前ベースの分散とエニーキャストを組み合わせることもできる。[5]

RFC 4786は、エニーキャストによるサービス分散に固有の運用上の制約を複数文書化している。[5]

- トランザクション状態と持続時間：エニーキャストは、長時間のトランザクション、サーバー側のトランザクション状態保持、およびノード間のデータ同期に制約を課す。[5]
- 不均一な負荷分散：ルーティングトポロジーがキャッチメントの規模を決定するため、エニーキャストノード間で細粒度の負荷分散を達成することは難しく、エニーキャストが信頼性と粗粒度のスケーリングを支援する一方で、ノード間のリクエスト量やトラフィック負荷は概して不均衡なままとなる。[5]
- 可用性監視：観測される到達可能性がクライアントのネットワーク位置によって異なり、各ノードが担当するクライアント母集団も静的ではなく確実に決定的でもないため、エニーキャスト環境下での可用性測定はより複雑になる。[5]

## コンテンツデリバリーネットワーク相互接続標準（RFC 6707およびRFC 7336）

コンテンツ配信ネットワーク相互接続（Content Delivery Network Interconnection、CDNI）は、独立した複数のコンテンツデリバリーネットワークが相互運用し、あるCDNが別のCDNに代わってエンドユーザーへコンテンツを配信できるようにする仕組みである。[3] 動画やマルチメディアトラフィックの増加に伴い、商用CDN事業者が容量を拡張するとともに、多くのネットワークサービスプロバイダー（NSP）も独自のCDNを構築するようになった。[3] 単一のCDNだけではあらゆるエンドユーザーの接続ネットワーク近傍に地理的拠点や十分なリソースを確保できない場合があるため、個別のCDNを相互接続することで配信網と容量を結集し、コンテンツサービスプロバイダー（CSP）からエンドユーザーまでのエンドツーエンド配信を実現する。[3]

IETFはこの問題領域をRFC 6707（Informational、2012年9月、B. Niven-Jenkins、F. Le Faucheur、N. Bitar著）で定義し、全体アーキテクチャをRFC 7336（Informational、2014年8月、L. Peterson、B. Davie、R. van Brandenburg著）で確立した。RFC 7336はRFC 3466を廃止している。[3][4] CDNIモデルでは、CSPが権威ある上流CDN（`uCDN`）と契約し、上流CDNは自らリクエストを処理するか、NSP運用のCDNなど1つ以上の下流CDN（`dCDN`）へ配信を委譲する。エンドユーザーへ最終的に配信を行う下流CDNはDelivering CDNと呼ばれる。[3][4]

相互接続された配信フローでは、ユーザーエージェントが最初に上流CDNへ接続し、上流CDNはDNSリダイレクトまたはHTTPリダイレクトによってユーザーにより近い下流CDNへリクエストを転送できる。[3][4] RFC 7336は、反復型CDNIリクエストリダイレクト（上流CDNがローカルロジックに基づきクライアントを下流CDNのリクエストルーティングシステムへリダイレクトする方式）と、再帰型CDNIリクエストリダイレクト（上流CDNが先に下流CDNのリダイレクトインターフェースへ問い合わせ、その応答を取り込んでクライアントを下流のサロゲートサーバーへ直接リダイレクトし得る方式）を区別している。[4] 下流CDNが要求されたオブジェクトを保持していない場合は上流CDNから取得し、必要に応じて上流CDNがCSPから取得する。[3] CDNIのルールとメタデータは`CDN-Domain`（コンテンツ集合を表すFQDN）に対して適用される一方、`Distinguished CDN-Domain`はCDN間の取得またはリダイレクト専用に割り当てられ、クライアントのリクエストには現れない。[4]

| CDNIインターフェース | 動作タイミング | RFC 6707およびRFC 7336で定義された役割 |
| --- | --- | --- |
| CDNI Control Interface | 初期設定およびトリガー操作 | 管理操作を調整し、CSPの操作に応じてメタデータやコンテンツの事前配置、再検証、パージを行うTrigger Interfaceを含む。[3][4] |
| CDNI Request Routing Interface | 同期および非同期 | 上流CDNと下流CDNの間でDNSまたはHTTPによるリクエストリダイレクトを処理し、動的なフットプリント広報を交換する。[3][4] |
| CDNI Metadata Interface | 同期または非同期 | 相互接続されたCDN間で、CDN-Domain単位の配信メタデータおよび配信ポリシーを交換する。[3][4] |
| CDNI Logging Interface | リアルタイムおよびオフライン | 課金および運用の可視化のため、ピアCDN間で配信ログレコードを交換する。[3][4] |

## コンテンツデリバリーネットワークの限界、鮮度劣化、およびセキュリティリスク

コンテンツデリバリーネットワークの運用には、キャッシュの鮮度劣化、共有キャッシュにおけるプライバシー、サードパーティの障害、およびアセットの完全性に関わる運用上・セキュリティ上のトレードオフが伴う。[1][2][6][7]

HTTPは単一のエンドツーエンド鮮度モデルを採用しているため、下流キャッシュよりも長い鮮度保持期間をCDNに設定すると、下流キャッシュの効率が低下するおそれがある。[2] RFC 9213はこの相互作用を、`Age: 1800`、`Cache-Control: max-age=600`、`CDN-Cache-Control: max-age=3600`を伴って配信されるレスポンスの例で示している。30分が経過した時点で、オブジェクトはCDNキャッシュにとっては依然としてフレッシュである一方、600秒の上限に従う下流キャッシュにとっては既にステイルな状態として到達する。[2] さらに、オリジンサーバーに到達できない切断状態のキャッシュは、許可された条件下でステイルなレスポンスを配信することがある。[1]

外部CDNへの依存は、サードパーティの可用性に対する依存関係を生じさせる。[6] MDN Web Docsは、サードパーティCDNが障害を起こしたり、特定地域でブロックされたり、恒久的にサービスを終了したりした場合、それに依存するウェブサイトが正常に動作しなくなると指摘している。[6] BootstrapやjQueryなどのサードパーティ製ライブラリを外部CDNドメインから読み込む構成も、状況によってはパフォーマンスを低下させ得る。ブラウザはサードパーティホストへの追加のDNSルックアップと接続確立を行う必要があり、現代のブラウザはプライバシー保護とタイミング攻撃対策のため参照元サイトの識別子を用いた二重キー方式（double keying）でHTTPキャッシュをオリジンごとにパーティショニングしているため、同一のサードパーティライブラリであってもサイトごとに別途ダウンロードしなければならない。[1][6]

共有CDNキャッシュは、セキュリティおよびデータ分離のリスクも伴う。[1][6][7] サードパーティCDNが侵害されると、攻撃者が依存サイトの訪問者へ悪意のあるコンテンツを配信できるようになるため、サードパーティの静的アセットにはサブリソース完全性（Subresource Integrity、SRI）などのクライアント側保護策が必要となる。[6] パーソナライズされたレスポンスを`Cache-Control: private`と明示せずに共有キャッシュへ保存すると、あるユーザーのデータが他のユーザーに露出するおそれがあり、Cookieの存在だけではHTTPレスポンスは非公開とみなされない。[7] RFC 9111はさらに、キャッシュポイズニング、タイミング攻撃、および機密情報のキャッシングをHTTPキャッシングシステムの中核的なセキュリティ考慮事項として挙げている。[1]

## よくある質問

### コンテンツデリバリーネットワーク（CDN）とは何ですか？

コンテンツデリバリーネットワーク（CDN）とは、ウェブコンテンツの複製を保存し、エンドユーザーに近いエッジロケーションからリクエストを処理する地理的に分散したサーバー群です。クライアントとオリジンサーバーの間でマネージド共有HTTPキャッシュとして機能することで、遅延を低減し、オリジンサーバーの負荷を抑え、可用性を高めます。 [6][7][8]

### CDN-Cache-Controlは標準のCache-Controlとどのように異なりますか？

RFC 9111で定義される標準のCache-Controlディレクティブはブラウザと共有キャッシュ全般に広く適用されるため、階層ごとの細かな対象指定には制限があります。2022年6月にRFC 9213で標準化されたCDN-Cache-ControlはCDNキャッシュのみを対象としたDictionary Structured Fieldであり、パブリッシャーはCDN専用のキャッシュポリシーを設定でき、CDNはそのレスポンスに対してCache-ControlとExpiresを無視します。 [2][7]

### RFC 4786のBGPエニーキャストルーティングとは何ですか？

RFC 4786（BCP 126）に文書化されたグローバルスコープのBGPエニーキャストは、複数の独立した拠点から同一のIPサービスアドレスを広報し、ルーティングシステムが自身のトポロジーとリクエストの発信地点に基づいて、リクエストを処理するノードを決めます。ラウンドロビンDNSによる振り分けを必要とせず、サービスの信頼性と粗粒度のスケーリングを支援しますが、ノード間のトラフィック負荷は不均一になりやすい傾向があります。 [5]

### CDN相互接続（CDNI）とは何ですか？

RFC 6707で概要が示されRFC 7336でフレームワーク化されたCDN相互接続（CDNI）は、個別のCDN同士が連携し、権限を持つ上流CDNがエンドユーザーにより近い下流CDNへコンテンツ配信を委譲できる仕組みです。制御（トリガーインターフェースを含む）、リクエストルーティング、メタデータ、ロギングの4つのインターフェース領域を通じて配信を調整します。 [3][4]

### CDNはパーソナライズされたユーザーデータを露出したり、古いコンテンツを配信したりすることがありますか？

はい、その可能性があります。CDNは共有キャッシュとして動作するため、パーソナライズされたレスポンスにCache-Control: privateディレクティブを付与せずに保存すると、あるユーザーのコンテンツが別のユーザーに露出するおそれがあり、Cookieの存在だけではレスポンスは非公開とみなされません。さらに、下流キャッシュよりも長い鮮度保持期間をCDNに設定すると、下流キャッシュに到達した時点で既に期限切れ（stale）のレスポンスとなる場合があります。 [2][7]

### サードパーティCDNから静的ライブラリを読み込むことにはどのようなリスクがありますか？

MDN Web Docsは、静的アセットのセルフホスティングと比較して3つの欠点を挙げています。サードパーティの障害、地域ブロック、またはサービス終了によって依存するウェブサイトが機能しなくなること、侵害されたCDNがサブリソース完全性（SRI）などの対策がない限り悪意のあるファイルを配信し得ること、そして別オリジンへの接続によりDNSルックアップと接続のオーバーヘッドが増える一方で、ブラウザのキャッシュパーティショニングによりサイト間でのアセット再利用が妨げられることです。 [6]

## 引用できる文

- IETFは2022年6月、RFC 7234を廃止して置き換えるStandards TrackのHTTPキャッシング仕様としてRFC 9111（STD 98）を発行した。 [1]
- 2022年6月にAkamai、Fastly、Cloudflareの著者らによって発行されたRFC 9213は、CDNキャッシュ向けのHTTPレスポンスヘッダーであるCDN-Cache-Controlを定義している。 [2]
- RFC 9213では、対象指定キャッシュ制御フィールドを実装するキャッシュは、max-age、must-revalidate、no-store、no-cache、privateの各ディレクティブをサポートしなければならない。 [2]
- 2006年12月に発行されたRFC 4786（BCP 126）は、IGPまたはBGP上のIPv4およびIPv6エニーキャストを用いて複数拠点へサービスを分散させる運用プラクティスを文書化している。 [5]
- RFC 6707（2012年9月）とRFC 7336（2014年8月）は、コンテンツ配信ネットワーク相互接続（CDNI）の問題定義とフレームワークを規定している。RFC 3466を廃止したのはRFC 7336である。 [3][4]
- 現代のブラウザはプライバシー保護のためオリジンごとにHTTPキャッシュをパーティショニングしており、サードパーティCDN上のライブラリであってもウェブサイトごとに個別のダウンロードが必要となる。 [6]
- CDNなどのマネージドキャッシュは、ダッシュボード、API呼び出し、または再起動を通じた保存済みレスポンスの明示的な削除を可能にしており、これは基本のHTTPキャッシング仕様には含まれない機能である。 [7]
- 2026-11-23時点で、Amazon CloudFrontはデフォルトでオブジェクトをエッジロケーションに24時間キャッシュし、最小有効期限は0秒、固定の最大有効期限は設定されていない。 [8]
